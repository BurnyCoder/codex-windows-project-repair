# Design and source references

The [CLI wrapper](../src/codex_windows_project_repair/cli.py) delegates to configuration, planning, Windows, storage, and workflow modules. [`build_repair`](../src/codex_windows_project_repair/storage.py) deep-copies decoded state and replaces only selected `rootPaths` arrays. Other decoded values are retained; JSON formatting and numeric spelling are not byte-preserved on serialization. The [storage tests](../tests/test_storage.py) reverse the allowed edit and compare the synthetic input with the result.

## Boundaries

1. **Diagnosis and proposal:** [configuration](../src/codex_windows_project_repair/config.py) rejects duplicate keys and nonstandard numeric constants. [Planning](../src/codex_windows_project_repair/planning.py) accepts the observed dictionary layout and selected single-root records only. `inspect` classifies shape, not causation; it does not validate folder accessibility.
2. **Filesystem evidence:** [`probe_root`](../src/codex_windows_project_repair/windows.py) passes separate arguments to the selected distribution. Before checking a child, its immediate parent must satisfy both `test -d` and `test -x`. Execute permission alone also accepts executable files. An existing directory is translated with `wslpath -w`; only one terminal LF or CRLF is removed. Empty output or remaining CR/LF is rejected before checking that the Windows path is absolute and `Path.is_dir()` succeeds. Significant whitespace is retained. Child `-d`, `-e`, and `-L` predicates must all be false before a missing-root proposal; the plan separately requires `--detach-missing`. These observations are metadata checks, not proof of future access or permission to read/write every file. Races and filesystem errors represented as false predicates remain limitations. [Regression coverage](../tests/test_windows.py) uses mocked predicates and translation, not a live WSL filesystem.
3. **Worker lifecycle:** [`single_worker`](../src/codex_windows_project_repair/windows.py) uses a `Local\` named mutex for the resolved profile, excluding other tool workers in the **same Windows session**. [The scheduler](../scripts/schedule-repair.ps1) also refuses an existing profile-derived task name and uses `IgnoreNew` for that task. It registers no trigger and starts a task with the current user's interactive, limited principal. With `--wait`, Python polls the discovered executable name until at least six seconds of observed absence, with a 30-minute deadline. This does not prove an orderly shutdown or flushed app buffers. Direct `apply` without `--wait` checks current absence only. The separate 35-minute scheduler execution cap can interrupt cleanup.
4. **Backup:** [Storage](../src/codex_windows_project_repair/storage.py) copies and byte-checks the original JSON. SQLite's backup API creates a consistent database snapshot through a `mode=ro` source connection, including committed data in WAL. `quick_check` performs its documented structural checks, not a complete semantic/history validation. Both backup files are hashed in the manifest. The tool sends no SQL updates to the source database; read-only SQL access is not a promise that SQLite will never interact with WAL/SHM sidecars. JSON and SQLite snapshots are not one cross-file transaction.
5. **Commit:** after another process check and byte comparison against the original JSON, a flushed temporary file replaces it through `ReplaceFileW`, with metadata-merge errors enabled. Microsoft documents retention of selected properties such as creation time and DACL; this is **not preservation of every metadata field** (the replacement supplies the file ID). Some API failure states can leave names/content changed or the target missing. A reported failure is not an assurance of rollback. The separate verified backup remains necessary; see [recovery](recovery.md).
6. **Verification:** [`verify_backup`](../src/codex_windows_project_repair/workflow.py) validates backup hashes, requires each original legacy project ID, checks each previous assignment key and value, and compares original SQLite ID sets. It permits new records and does not compare every database field, external transcript, or UI grouping. The result retains `needs_ui_verification` even when all these comparisons pass. [Workflow tests](../tests/test_workflow.py) cover this distinction, including loss hidden by equal record counts and a removed null-valued association.

The scheduler pins reviewed plan bytes with a digest and resolves profile/output paths during preflight. Keep the checkout, environment, and plan trusted while it waits. This is not a security boundary against another process with the same user's privileges. CLI options, plan schema, and existing result fields are unchanged by the path-handling correction.

The tool does not exclusively lock all Codex state. A process can restart between observations; the guards reduce that race but do not eliminate it. Users must quit Codex normally and keep it closed during application. The process-name guard may also match an unrelated executable with the same name. Cross-session workers, hard termination, power loss, filesystem failures, and future internal-schema changes have not been validated as recovery-safe scenarios.

## Logging and status

[`cli.main`](../src/codex_windows_project_repair/cli.py) creates UTC-named logs for `plan` and `apply`, including `--check-only`, and sends log events to stderr as they are emitted. Completed diagnostic subprocess output is captured by `subprocess.run` and logged **after completion**, not streamed from the child. A timeout or failure before the logging call can leave captured output unlogged. Byte decoding uses a UTF-16/UTF-8 heuristic and replacement characters for decoding errors. This is not an exact binary transcript.

`inspect` and `verify` print results and diagnostic stderr without creating report/log files. Operational result JSON and caught runtime tracebacks are logged after logger setup; argument/configuration/log-initialization failures may precede it. Status updates begin inside the application workflow, so early CLI or mutex failures may leave no new status. Scheduler transcripts cover their active recording interval; errors before startup or rendered after `Stop-Transcript` can be absent. No LLM calls or telemetry are implemented in this utility. Tool installation, WSL, and Codex have their own behavior outside this scope.
