# Maintainer guidance

Use native Windows, Python 3.14, uv, and the local environment. Keep the public CLI as a wrapper over named phases; isolate Windows calls from pure state transformations. Preserve the existing seven regression cases and add a failing safety-contract test before a behavioral fix.

Never test application on a developer's real Codex profile. Use disposable synthetic JSON and SQLite fixtures. Do not weaken backup verification, process guards, plan/profile binding, or explicit project selection to make a test pass. No source-database writes belong in the repair.

Keep all runtime data under ignored directories. Before publishing, inspect the staged diff and Git history for private paths, identifiers, databases, logs, credentials, and accidental author emails. Use synthetic labels in examples. Never upload real diagnostic or backup files.

Update the relevant documentation when behavior changes. Keep usage in [README](README.md), rationale and API sources in [design](docs/design.md), restoration steps in [recovery](docs/recovery.md), and observations in [case study](docs/case-study.md) and [validation](docs/validation.md). Distinguish public code/tests, primary API documentation, private measurements, and hypotheses. Pin historical evidence to revisions and CI jobs; date private observations and state their inspection windows. Public documentation is not independent proof of a private run. Attribute user-reported recovery to the user; do not infer UI verification, complete migration, universal compatibility, orderly shutdown, or all-error resolution from narrower checks.

Run the documented fixture tests, CLI help, and build for relevant changes. A scheduler integration run creates temporary Windows tasks and needs an interactive session; run it only when this system activity is permitted. A request not to launch workers takes precedence, including for fixture workers. Keep historical scheduler evidence separate from current runs. Review correctness, preservation, security, and failure paths once, fix substantive findings, then publish through a feature PR with passing Windows CI. Explain code locally without claiming broader guarantees than the implementation/tests establish.
